# Where the toolkit can show value: options after the 2026-09-17 ablation

Written 2026-09-22. The corrected ablation says the schema and renderer do not
raise the full-chain pass rate over a frontier model that writes the `.fr`
file by hand. This note says why that experiment could not show toolkit
value, and lists the experiments that can. Every number below comes from the
corrected harness (`ABLATION_2026-09-17.md`, `ablation_report*.json`,
`repair_repair_corrected_report.md`).

## 1. Why the ablation could not show a toolkit effect

**It tested the smallest part of the toolkit.** The "tools" arm had Read,
Grep and Glob, the Pydantic schema and the renderer. Nothing else. No
`validatemodel`, no `jobs`, no repair round, no `reverselagrangian`
crosscheck, no `arxivsource`. Validation ran afterwards, by the harness, in
both arms (`subagent_bench.py`, `ALLOWED_TOOLS`). So the measured quantity is
"structured spec plus renderer" against "hand-written `.fr`", one shot. A
frontier model already writes FeynRules syntax well, so the spec removes an
error class the model rarely hits, and adds a translation step with its own
leaks (`\theta _c` in a UFO name; the ALRM spec the schema rejected).

**Both arms hit the same wall, and the wall is a harness design choice.**
Every run writes an add-on that loads on top of `SM.fr`. The SM fields
`Phi`, `vl`, `Z` are declared in `SM.fr`, so an add-on cannot rotate the
Higgs or the neutrinos into the mass basis. The reference models in the
FeynRules database are full models: 24 of the cached reference files
redefine `Phi[2]` themselves. The repair agent on B-L-SM round 3 wrote this
out explicitly: the `H`-`H2` cross term "must live in the SM doublet Phi's
neutral-component Definitions, which is declared in the externally supplied
base SM.fr, outside this task's editable scope". This class is the dominant
failure now:

| set | arm | runs checked | `mass_diagonal` fail | `hermiticity` fail |
|---|---|---|---|---|
| 16 papers, Sonnet | tools | 15 | 10 | 5 |
| 16 papers, Sonnet | no tools | 14 | 7 | 4 |
| 4 models, Opus | v3 tools | 8 | 2 | 3 |
| 4 models, Opus | v3 no tools | 8 | 1 | 3 |

Seven of the nine models still open after the repair loop fail this check.

**The samples cannot separate the arms.** Fisher exact tests on the
published comparisons:

| comparison | p |
|---|---|
| Opus, full chain, tools 2/8 vs no tools 4/8 | 0.61 |
| Sonnet, full chain, 2/15 vs 2/15 | 1.00 |
| Sonnet, MadGraph import, 7/15 vs 4/15 | 0.45 |
| Sonnet, compiled, 13/15 vs 11/15 | 0.65 |
| repair loop, 5/16 to 7/16 | 0.72 |

To detect a rise from 25% to 50% with the usual power you need about 58
papers per arm. To detect 13% to 33%, about 68. The benchmark has 16
scorable single-model papers. Any claim in either direction from the current
tables is noise, including "the toolkit hurts".

**The metric hides where the toolkit acts.** Full-chain pass is one bit per
run. The stages the toolkit touches (syntax, UFO serialisation, MadGraph
import) went the toolkit's way on the 16-paper set (compiled 13 vs 11,
MadGraph 7 vs 4), and the stage it cannot touch (mass basis) decided the
final bit.

## 2. Options, ranked

Each option gives one honest claim that the current design cannot. Cost is
in days of work plus Wolfram wall-clock, which is serial on one kernel.

### A. Close the mass-basis wall with a capability the agent will not perform blind

The agent recognises the mixing and refuses to rotate fields without a
derivation, which is the correct behaviour under the "do not change the
physics" rule. A tool can do the derivation.

1. **SM overrides in the schema.** Add a slot that redeclares an `SM.fr`
   class (`Phi`, `vl`, `Z`, `W`) with new `Definitions`, and make the
   renderer emit it after the SM block. This is what the reference models do
   by hand. The no-tools arm gets the same permission in its prompt, so the
   comparison stays fair.
2. **A `massbasis` tool.** Input: the gauge-basis Lagrangian, the declared
   gauge and mass bases, the mixing angle name. The tool runs FeynRules'
   own `ComputeMassMatrix` (`Core/MassDiagonalization.m`,
   `M$MixingsDescription`) on the Wolfram kernel already in the chain,
   solves the diagonalisation, and returns the Internal parameter
   definitions in the inverted parametrisation (physical masses and angle
   external, potential couplings internal) so `CheckDiagonalMassTerms`
   passes symbolically. The agent pastes the result; it never rotates
   blind. FeynRules 2.x ships the machinery (arXiv:1301.5932): the agent
   declares `M$MixingsDescription` with `MassBasis`, `GaugeBasis` and a
   `MixingMatrix`; FeynRules fills the field `Definitions` itself;
   `WriteASperGe` plus `RunASperGe` diagonalise numerically and load the
   values back before `WriteUFO`. The `bsm_agent` backend
   (arXiv:2606.21316) derives tree-level mass matrices deterministically
   from quantum numbers and is a second source of the same computation.

Experiment: three arms on the 10 mass-mixing runs plus the 7 open repair
models. No tools with override permission; tools with the override slot;
tools with the `massbasis` tool. The claim, if it holds: the tool converts
the dominant failure class that neither prompt rules nor a frontier model
convert. Cost: about a week to build, two days of Wolfram time. Risk:
FeynRules' symbolic check may not simplify an inverted parametrisation for
every potential, and the ASperGe path fixes the mixing values at export
time, so whether `CheckDiagonalMassTerms` passes after the mixing module
fills the definitions must be tried on one model (pNG is the simplest) in
the first day, before the rest is built.

### B. Measure the closed loop, not the one-shot spec

The toolkit's product is generate, validate, repair. The repair loop went
5/16 to 7/16 with the toolkit's `VALIDATION_REPORT.md` (check verdicts,
prose explanation per check, heuristic error tags, MadGraph first
traceback). What is missing is the control: the same repair agent given the
raw `compile.log` tail and nothing else. Earlier phases saw blind repair go
0/5 on UFO-serialisation leaks and become routine once pinpointed, but those
rounds ran with the invalid classifier and were never re-done.

Experiment: `repair_subagent.py` with a `--report raw` variant that hands
the agent only the log tail. Same 16 papers, same three rounds, same model.
Claim: the toolkit's diagnostics, not the model, decide which defects get
fixed. Cost: two days, mostly Wolfram time.

### C. Best-of-n with the chain as the oracle

On the 4-model Opus set the per-run pass rate is 2 to 5 of 8, but the pass
rate per model when any seed passes is 2 to 3 of 4, and the union over arms
and seeds is 4 of 4. On the 16 papers the union is 3 of 16 from two runs
each. A user without the chain cannot pick the passing seed. With it, the
pipeline is "sample n, validate, keep the first that passes".

Experiment: 4 seeds per paper, one arm, report pass@1, pass@2, pass@4 with
the chain as selector, against pass@1 without it. Claim: the validation
chain is what turns a 25% generator into a usable one. Cost: one to two
days of Wolfram time on existing scripts (`subagent_bench.py --seeds 4`).

### D. Weaker and open models

The scaffolding literature says structure helps small models most and
frontier models least, and one HEP benchmark measured exactly our design.
HEPToolBench 1.2 (arXiv:2608.28232) compares native syntax against a
schema-mediated JSON that deterministic code serialises, on 28 MadGraph
card tasks and 42 deployments: 41 of 42 improve, and the gain sits in
models under 50B parameters (2/125 to 81/125 passes). The format-tax
papers (arXiv:2606.09410, 2608.21747, 2607.03953) find the same split:
Sonnet unchanged, Haiku and small open models down 30 points or up 40
depending on whether the format is imposed or offered. Sonnet 2/15 vs 2/15
and Opus 2/8 vs 4/8 are both frontier results, so the ablation ran on the
one class of model where no effect is expected. `ExtractLagrangianTool`
already speaks Ollama, vLLM and LiteLLM.

Experiment: Haiku 4.5 and one open-weights model, tools vs no tools, on the
16 papers. Claim, if it holds: the schema and renderer let a cheap model
produce a compilable file at all. Risk: 0 vs 0 is a real possible outcome.
Cost: one day of agent time, one day of Wolfram time.

### E. Deterministic lints before the compile

The 15 construct rules in `prompt_addendum_v3.txt` each came from a real
compile or import failure, and all of them are machine-checkable on the
`.fr` text: protected names, `InteractionOrder` on every coupling, pattern
rules on tensor parameters, primes in particle names, explicit indices in
`DC[]`, one declared total, `AddGaugeRepresentation` for non-fundamental
representations, `$` in symbol names, `SelfConjugate` with quantum numbers.
A lint runs in milliseconds; a compile takes up to 900 s and a sextet stall
takes 3600 s and still fails.

Experiment: implement the lints in `validatemodel`, replay every stored `.fr`
from the reruns and the repair rounds (about 120 files), and count how many
compile or import failures the lints predicted. Then one repair round with
lint output only. Claim: the toolkit catches X% of construct defects before
a 15-minute compile, and the agent fixes them on the first round. Cost: two
days, no Wolfram time for the replay.

### F. Score the crosscheck as a defect detector

The five physicist findings were never used to measure the toolkit's own
reviewer, `reverselagrangian crosscheck`. Recall on the confirmed findings
was 3 of 4 at best, and the Z_R finding was missed because both readers
used the same flattened text. That is a measurable precision and recall.

Experiment: mutation testing. Take the models that pass the full chain,
inject one known defect each (drop `Eps`, flip a U(1) charge sign, drop a
`1/Lambda` factor, drop `CC[]`, change a normalisation), run the crosscheck
against the LaTeX source, and score detection. Add the five real findings
as the held-out positives. Claim: the toolkit finds the errors physicists
found, plus a stated fraction of injected ones, on files the compile chain
passes. This is the claim Ian and Konstantin asked for in effect. Cost: two
days, no Wolfram time.

### H. Publish the benchmark and run the competitor on it

Nobody else reports a pass rate for `.fr` generation from a paper.
ColliderAgent (arXiv:2603.14553) ships Claude Code skills that generate
and validate FeynRules models and reports "often consistent" on 8
benchmarks with 3 runs each. MadAgents (arXiv:2601.21015) uses a
pre-existing UFO and reports one end-to-end run. Our 16-paper set, the
contamination audit, the LaTeX sources, the corrected checks and the
name-agnostic predicates are the only quantitative instrument in the
field. Running ColliderAgent's skills through `agent_bench` on the same 16
papers, with the same sandbox and audit, gives a number nobody has: how a
second toolkit does on a fixed, contamination-controlled set. Claim: the
benchmark is the contribution, and the toolkit is the reference
implementation that the field can be measured against. Cost: three days,
plus one day of Wolfram time per toolkit.

### G. Grow the benchmark

None of A to F fixes the power problem. The FeynRules database index has 646
entries; the single-model filter admitted 16 of 28. Reaching 60 scorable
papers means running `single_model_select.py` over the wider database and
fetching LaTeX sources. Cost: a week of curation, then every later
experiment costs about four times the Wolfram time.

## 3. Recommended order

1. **F and E first.** No Wolfram time, two days each, and each gives a
   claim that stands alone: the toolkit finds physics defects the compile
   passes, and it catches construct defects before the compile.
2. **A next.** It is the only option that attacks the failure class that
   decides the headline number, and it is the one thing a frontier model
   provably does not do on its own.
3. **B and C after A**, because the closed loop and best-of-n both get
   better once the mass-basis class stops absorbing every retry.
4. **H in parallel with A.** It needs no new toolkit code, only the
   competitor's skills in the driver, and it turns the benchmark itself
   into the deliverable.
5. **D and G** when there is budget. D is the cheapest positive story if it
   works; G is what makes any of the numbers publishable.

## 4. What to say now

The honest one-paragraph version for Tony, Ian and Konstantin: the ablation
tested the schema and renderer alone and found no effect at a sample size
that could not have found one. The full-chain failures are now a physics
class the add-on design cannot express. The toolkit's measurable value lies
in the parts that were not in the ablation: the validation chain as a
selector and diagnostic, the crosscheck as a reviewer, and a mass-basis tool
that does the one step the model declines to do blind. The experiments
above measure each of those separately.

## 6. Results so far (2026-09-22, same day)

- **F, done.** `CROSSCHECK_MUTATION_2026-09-22.md`: 31 of 31 injected
  physics defects named by the crosscheck, all of which pass the compile
  chain unchanged; 4 of the 5 September findings named on the LaTeX source
  (the Higgs charge sign is still argued the wrong way); controls draw a
  mean of 3 other substantive items, mostly genuine omissions in the base
  files.
- **E, done.** `LINT_REPLAY_2026-09-22.md`: on 140 stored files the
  harness-stage lint is 8/8, the mass-mixing lint predicts a failed mass
  check 22 times in 26, the MadGraph rules are 50 to 64% precise, and
  compile timeouts are not lintable.
- **A, first result.** `MASSBASIS_2026-09-22.md`: the stored pNG one-shot
  had the inverted parametrisation exactly right (sympy: all cross terms
  zero) and failed on three symbol names and a double-counted SM Higgs
  sector. With the names fixed and `LTotal := LSM - LHiggs + LScalarPng`,
  the file passes the full chain (all four checks, MadGraph import, 75 s),
  and the UFO's `h2 t t~` vertex carries `-(I st yt)/Sqrt[2]`, so an add-on
  CAN redeclare `Phi` and the override reaches the SM Yukawa sector. The
  toolkit feature is an `sm_overrides` slot plus the `massbasis.py`
  derivation.

## 5. Related work (survey of 2026-09-22)

**Agents that write or drive model files.**

- ColliderAgent, Qiu et al., arXiv:2603.14553. Claude Code skills
  `feynrules-model-generator`, `feynrules-model-validator`,
  `ufo-generator`; checks Hermiticity and loads the UFO in MadGraph. No
  mixing tool. 8 reproduced benchmarks, 3 runs each, no pass rate.
- MadAgents, Plehn, Schiller, Schmal, arXiv:2601.21015. Agents run MadGraph
  from a paper with an existing UFO. One end-to-end run reported.
- bsm_agent, Saad, arXiv:2606.21316. Deterministic Python backend builds a
  renormalisable Lagrangian from quantum numbers, checks anomalies and
  derives tree-level mass matrices. Does not read papers or emit `.fr`.
- HEPTAPOD, Menzo et al., arXiv:2512.15867, and Agentic Diagrammatica,
  arXiv:2603.26990, argue for the compact-spec-plus-trusted-backend design
  that the schema and renderer implement.
- Transformers for Lagrangians, Koay et al., arXiv:2501.09729. Custom model,
  particle list to Lagrangian, not FeynRules.
- Adjacent: AgentRivet arXiv:2606.13535, HEP code from publications
  arXiv:2604.14696, SMEFT-Pheno-Agent arXiv:2607.22331.

**Benchmarks.** HEPToolBench 1.2, arXiv:2608.28232 (MadGraph cards, no
FeynRules tasks, schema-mediated output helps small models). Collider-Bench,
arXiv:2605.13950 (analysis reproduction; no agent beats the physicist in
the loop). HEPLocalAgent, arXiv:2608.28244 (47 cases, 7 valid artifacts
first try, 19 after repair). SciCode-Verified, arXiv:2608.04975.

**Mass diagonalisation.** FeynRules mixing module and ASperGe, Alloul et
al., arXiv:1301.5932, in FeynRules 2.0 (arXiv:1310.1921):
`M$MixingsDescription`, `ComputeMassMatrix`, `MixingSummary`,
`WriteASperGe`, `RunASperGe`. SARAH, arXiv:1503.04200, declares rotations in
`DEFINITION[EWSB][MatterSector]` and diagonalises in SPheno. Both keep the
symbolic step in the model tool and the numeric step downstream, which is
the split option A proposes.

**When scaffolding helps.** Let Me Speak Freely, arXiv:2408.02442; The
Format Tax, arXiv:2604.03616; Capacity, Not Format, arXiv:2606.09410;
Less Is More, arXiv:2604.21746; Architecture as Capability Equalizer,
arXiv:2608.21747; natural-language tools, arXiv:2607.03953. The consistent
result: imposed structure costs frontier models little or nothing and
costs small models a lot, while offered structure with deterministic
serialisation helps small models most.

**Project context.** ML4SCI HEPSIM5 proposal:
https://ml4sci.org/gsoc/2026/proposal_HEPSIM5.html. Midterm PR:
https://github.com/tonymenzo/heptapod/pull/23. The S1 leptoquark example
is now used by ColliderAgent and MadAgents as well, so it is an informal
shared test case.
