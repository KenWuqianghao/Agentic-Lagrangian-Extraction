The paper Konstantin mentioned

It is your own team's

arXiv:2603.26990, Agentic Diagrammatica — Menzo, Roman, Fleming, Gleyzer, Matchev, Mrenna. FERMILAB-PUB-26-0208-T. It describes a symbolic-computation extension to the same HEPTAPOD framework this project contributes to. Konstantin is an author; Tony is reviewing the PR.

The most likely ask is named in their own conclusions.

"automatic parsing of UFO model files from FeynRules into FeynGraph vertex rules for BSM diagram enumeration without manual model specification."

One of three EDA extensions they list, and the only one whose input is exactly what this pipeline already produces and validates at scale. Two cheaper options exist: the paper explicitly invites other groups to attempt its two benchmark tasks and report back, with both prompts printed verbatim; and the 28-model FeynRules benchmark is the "Task 3" the paper lacks, since both of its benchmarks assume the model is already known.

A correction to my own first reading.

Research initially concluded this pipeline is the free-form code-generation pattern the paper argues against. Checking the source disproved it. GenerateFeynRulesModelTool takes a schema-validated spec, and render.py states that the convention-dependent Mathematica syntax "is built here in tested Python". Agent says what, trusted backend fixes the conventions — that is their tool-constrained architecture, arrived at independently in a second domain. A confirming instance, not the anti-pattern, which is a far better basis for pitching Task 3.

Benchmark infrastructure

Three ways it lied before the checks existed

The goal was infrastructure for "which model best drives the physics toolkit". Each of these was caught by running it, and each would have produced a credible-looking number.

01
The toolkit was never served
The first run made 4 tool calls, gave a plausible answer, and never touched HEPTAPOD — it reached arxiv.org through a generic fetch tool. A benchmark scoring only the answer would have recorded a pass.
fix → per-run MCP config serving only heptapod
02
It inherited the operator's own MCP servers
Whatever the person running the benchmark happens to have configured leaked into the agent's toolbox. That silently changes the question from "how well does this model drive the toolkit" to "how resourceful is this model in general" — a different question, with a flattering answer.
fix → --strict-mcp-config
03
Built-in shortcuts bypassed the physics tools
With the toolkit correctly served, a run still curl'd the archive's HTTP API directly, produced the correct number, and scored PASS — having used no physics tool at all. Only the separate required-tool check caught it.
fix → --disallowedTools Bash,WebFetch,WebSearch

A fourth issue was an argv bug rather than a lie: --disallowedTools is variadic and swallowed the trailing positional prompt, so every case exited in two seconds looking like a model failure. The prompt now goes on stdin.

casetiercallsrequired toolsscore
t1-arxiv-astro-searchI3 ok unscored
t2-exoplanet-disagreementII3 ok pass
t2-frgen-leptoquarkII15 ok pass

Tier I has no artifact scorer yet and is reported unscored rather than counted as a pass. Only Claude has credentials here; codex and orchestral are declared with an explicit reason so a run says "no usage left" rather than quietly comparing one model against nothing.

New workstream

Why do two papers disagree about a planet?

A new exoplanet bundle checks a paper's claimed measurements against the NASA Exoplanet Archive. Three premises in the original brief turned out to be wrong, all corrected by querying the service directly.

verified

Only one table can answer it

ps holds one row per planet per published reference; pscomppars holds one composite row. HD 189733 b: 21 rows versus 1. Asking why papers disagree from pscomppars is structurally impossible — it has already discarded the disagreement. A test asserts it never appears in this path.

premise wrong

ps cannot name the telescope

Its three facility columns all describe the discovery and are identical on every row — all 21 read "Haute-Provence Observatory" while the radii come from Spitzer, HST and ground-based work. Per-instrument attribution exists only in transitspec / emissionspec, so the two halves are reported separately rather than fused into a causal claim the archive cannot support.

premise wrong

The atmospheres URL is not an API

nph-firefly?atmospheres returns HTTP 200 and 31 KB of JavaScript shell with no data. The real per-instrument spectroscopy is in the TAP tables above.

Example 5 · an agent answering the question, end to end

prompt — "Find out how many separate published parameter sets the NASA
Exoplanet Archive holds for HD 189733 b, and state that number explicitly.
Then say which parameter shows the largest disagreement between references."

27.0 s · 3 tool calls

  ● "I'll look up the relevant tools for querying the NASA Exoplanet
     Archive and measurement disagreements."

  ToolSearch  select:Resolveplanetname,Exoplanetarchivequery,
              Publishedmeasurements,Measurementdisagreement
  ToolSearch  "exoplanet archive query"

  ● "Now I'll query the disagreement tool directly for HD 189733 b."

  mcp__heptapod__Measurementdisagreement
     { "planet_name": "HD 189733 b", "include_spectroscopy": true }

  ● "The NASA Exoplanet Archive holds 21 separate published parameter
     sets for HD 189733 b. Of the three parameters checked, the
     orbital period shows the largest disagreement... the most
     discrepant pair (Kokori et al. 2023 vs. Stassun et al. 2017)
     differs by 4.75σ — even though the raw spread in period
     values is small..."

  score    ✓  21 confirmed by an independent archive query
  required ✓  Measurementdisagreement was actually called

One call does the work: it pulls all 21 published parameter sets, compares every pair that carries error bars, and separately fetches the 201 spectroscopy points. The agent's closing remark — "even though the raw spread in period values is small" — is the tool earning its keep. The period values differ only in the fourth decimal, so eyeballing them suggests agreement; they are precise enough that the difference is still 4.75σ.

Both checks had to hold. An earlier run got 21 correct by running curl against the archive's web API and was marked a failure — right answer, no physics tool touched, and therefore no evidence about driving the toolkit.

What it finds on HD 189733 b, live.

10 published radii spanning 12.3–14.12 R⊕, with the most discrepant pair 4.1σ apart (Stassun 2017 vs Bouchy 2005). Orbital period contested at 4.7σ — a transit-timing signature. 201 spectroscopy points across 8 instruments once names are normalised.

The 4.7σ period result was invisible at first. Tension was computed between the minimum and maximum values, and the extremes are frequently the rows without error bars — so the tool reported "no uncertainties quoted" for a planet where 14 of 18 references quote them. It now compares every pair that has uncertainties.
