A 27B open model in the heptapod pi harness passes twice as many papers as one-shot Claude Code

We built a custom agent harness on pi that puts the heptapod validation chain inside the agent loop, and ran it on the 16 single-model papers of the September ablation. Same papers, same task text, same scorer for every arm.

The harness doubles the one-shot Claude Code pass count with a much smaller open model, and it clears the check that sank most one-shot runs: mass_diagonal. The same-model gain is significant on compilation and on the mass check. The gain over Claude Code is not significant at n = 16, and the cleanest test, the harness on Sonnet itself, could not run (pi bills Anthropic models as extra usage).

Physics fidelity: did the harness pass by deleting physics?

The harness optimises against the same chain that scores it, so a pass could in principle come from dropping the hard terms. Two independent measures say it did not, with one clear exception.

ArmMean field F1 vs reference .frRuns scoredPhysicist-finding predicates
  • Field F1 rises from 0.66 (Claude Code) and 0.64 (plain Qwen) to 0.77 with the harness: its models carry more of the reference fields, not fewer.
  • The exception: EffLRSM Z_R normalisation. The harness model passes three of four checks but has the September Z_R factor wrong, which both one-shot arms had right. The consistency checks cannot see a normalisation, and the referee was not run on this paper. Passing the chain is not the same as reproducing the paper.
  • The independent referee (a second pi agent with a fresh context, paper and file only) ran on 5 of 16 papers. On pNG it found no physics discrepancy and argued, from the paper's own direct-detection formula, that a sign in the paper's appendix is the typo.
  • The agent's own verdicts were honest. In 13 runs that called validate_model, the agent's last in-loop verdict was a pass 4 times, and the independent re-score confirmed all 4.

What the harness changed

The mass-basis wall

Mass-diagonal passes went from 5 (Claude Code) and 3 (plain Qwen) to 10. The protocol gives the SM-override recipe, LTotal := LSM - LHiggs + … with the redeclared Higgs doublet, and massbasis derives the inverted couplings symbolically. On pNG the agent wrote a three-field spec with the soft-breaking term unprompted.

Compile errors caught in the loop

Plain Qwen compiled 4 of 16 files. With lint and validation in the loop, 11. The pilot surfaced two defects the old reports hid: an unclosed (* that commented out the whole model, and an edit that dropped a closing brace. Both are now lint rules.

The new bottleneck: MadGraph

Seven harness models pass all four FeynRules checks; three of them (B-L-SM, HeavyN, Wprime) then fail the MadGraph import. The next diagnostic to add is the UFO import error itself, surfaced in the report.

The harness re-sends its whole context every turn, so it reads about 70 times the input of a one-shot run. With self-hosted models that is GPU time, not a bill per token, but it is the obvious target for the token-efficiency pass that comes next.

Limits of this result

  • n = 16, one seed per arm. Only the same-model effects on compilation and on the mass check reach p < 0.05. About 58 papers per arm would be needed to detect 25% → 50% on the full chain.
  • Different models across the headline comparison. "Beats Claude Code" compares the harness on Qwen3.8-27B with Claude Code on Sonnet 5. The harness on Sonnet could not run: Anthropic rejects Claude Max logins from third-party apps unless extra usage is funded.
  • The harness sees the scoring chain. That is the design, and it is why field F1, the physicist-finding predicates and the referee are reported alongside the pass count.
  • Infrastructure noise. Two runs lost to GPU-proxy disconnects were re-run once, by rule. Two harness runs (331, GeneralU1) ended on a text-only turn with no model and count as failures. Two harness runs hit Qwen's 262k context but still delivered.
  • gpt-oss harness incomplete. The second GPU account was disabled after 5 of 16 papers, each cut off mid-loop. Plain gpt-oss compiled 2 of 16, so the large-model arm says little either way.
  • The pilot was excluded. The pNG pilot passed on validation 4 while two lint rules were being added; the benchmark re-ran pNG on the final code (it passed again).

Conclusions

  1. The toolkit's value shows up once it sits inside the loop. The September ablation tested a schema and renderer in one shot and found nothing. Validation, lint and a mass-basis tool in the loop turn a model that compiles 4 of 16 files into one that matches Claude Code on compilation and doubles its full-chain passes.
  2. The gain lands where predicted. The mass-diagonal failure class, which neither prompt rules nor a frontier model fixed in one shot, is the one the harness converts.
  3. The claim that holds today: same model, the harness is significantly better at producing compilable, mass-diagonal models. The claim against Claude Code is directionally positive and not yet significant.
  4. Checks are not fidelity. The EffLRSM normalisation miss shows the referee must run on every model, not by choice.

Next steps

  1. Run the harness on Sonnet 5 (API key or funded extra usage) against the same Claude Code baseline: the clean comparison.
  2. Make review_model mandatory before the agent may stop, and add a continue guard for text-only turns (331, GeneralU1).
  3. Report the UFO import error in validate_model, the new bottleneck.
  4. Apply the Cursor token-efficiency audit to the harness, measured as tokens per completed model.
  5. Three seeds per arm and the remaining gpt-oss harness runs, when GPU budget allows.
