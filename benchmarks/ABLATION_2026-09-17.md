# Ablation, corrected checks (2026-09-17)

Every number here comes from the corrected harness: FeynRules check verdicts
read from the checks' return values (`tools/feynrules/lagrangian_checks.py` on
heptapod `main`), `LSM` added only when a model's total does not already reach
it, and the full chain re-run end to end (compile, four default checks,
MadGraph import). The old classifier, which could not report a failure, is
gone. The generated tables are `ablation_report.md` (the four reviewed models)
and `ablation_report_single_model.md` (the 16 single-model papers).

## 1. The four reviewed models, Opus 5, two seeds per arm

| arm | paper source | tools | findings resolved | compiled | all checks | MadGraph | full chain | field F1 |
|---|---|---|---|---|---|---|---|---|
| v1, original prompt | PDF text | yes | 4/8 | 6/8 | 3/8 | 2/8 | 2/8 | 0.90 |
| v2, physics rules | PDF text | yes | 6/8 | 7/8 | 4/8 | 3/8 | 3/8 | 0.88 |
| v3 rules, framework | LaTeX | yes | 7/8 | 6/8 | 2/8 | 5/8 | 2/8 | 0.83 |
| v3 rules, no tools | LaTeX | no | 7/8 | 7/8 | 4/8 | 7/8 | 4/8 | 0.86 |
| v3 rules, framework | PDF text | yes | 5/8 | 6/8 | 5/8 | 6/8 | 5/8 | 0.84 |

What this says:

- **The physics rules and the LaTeX source fix the reviewed defects.** Runs
  with every finding resolved go from 4/8 to 7/8. That result was already
  true before the correction and still is: the finding checks read the
  model text.
- **The toolkit does not raise the chain pass rate.** With every tool taken
  away, the agent wrote the `.fr` by hand and passed the full chain in 4 of 8
  runs against 2 of 8 with the framework. This is the same direction as
  before the correction, with lower absolute numbers.
- **The PDF-text arm did best on the chain, 5 of 8.** It resolved fewer
  findings (5/8). Eight runs per arm is too few to rank the v3 arms against
  each other on the chain; the two conclusions above are the ones the data
  supports.
- **What fails now is physics, not syntax.** Across the v3 arms the dominant
  failure is a non-diagonal mass term with an inconclusive mass spectrum,
  then Hermiticity. Both were invisible before the correction.

The sextets are unchanged: three of four seeds per arm time out at 900 s, and
the fourth compiles and fails Hermiticity.

## 2. All 16 single-model papers, Sonnet 5, one seed per arm

The 16 papers are the ones `single_model_papers.md` marks as defining exactly
one model with a scorable reference. Both arms use the same model, the same
LaTeX source and the same v3 rules, so the only difference is the toolkit.

| arm | runs with a model | compiled | all checks | MadGraph | full chain | field F1 |
|---|---|---|---|---|---|---|
| tools | 15/16 | 13/15 | 3/15 | 7/15 | 2/15 | 0.67 |
| no tools | 15/16 | 11/15 | 4/15 | 4/15 | 2/15 | 0.66 |

The reviewed-finding checks apply to three of these papers. The no-tools arm
passed three of the four predicates; the tools arm passed two. The Z_R
normalisation is the one that separates them, and the no-tools arm got it
right.

- **Two passes each, and not the same two.** Tools: 331 and Chern-Simons
  portal. No tools: Chern-Simons portal and pNG dark matter.
- **The model matters more than the toolkit.** On the three papers both
  model families ran, Opus passed the full chain in 2 of 6 framework runs and
  4 of 6 no-tools runs. Sonnet passed 0 of 3 in each arm.
- **The runs that produced no model.** The 331 no-tools run hit the 64k
  output-token limit twice and delivered nothing; the 331 tools run, whose
  output is a compact spec, compiled and passed. The ALRM tools run produced
  a spec the schema rejected (a multi-member class without a flavour index),
  so the structured path rendered nothing. The Wprime no-tools run declared
  two totals and could not be scored.
- **Policy slips.** Eight of the 16 Sonnet tools runs called Bash, which the
  policy forbids. Every call stayed inside the sandbox (grep, sed, wc on the
  paper and the schema, or a bare `true`), so no run read anything it was
  not given. These runs are marked `audit_ok=False` and counted as clean of
  contamination. One no-tools run called an unrelated tool once; same
  treatment.

## 3. The repair loop, re-run with the corrected checks

The old repair-loop numbers (15/28 to 25/28) are void: that loop stopped
repairing when it saw a pass, and the passes were fake. This is a fresh run on
the same 16 single-model papers, from each paper's one-shot model, three
rounds, Sonnet 5 as the repair agent, and the corrected checks driving every
round. The report is `repair_repair_corrected_report.md`.

| stage | full chain |
|---|---|
| one-shot | 5/16 |
| after round 1 | 5/16 |
| after round 2 | 7/16 |
| after round 3 | 7/16 |

- **What the loop fixed.** Chern-Simons portal (no total Lagrangian declared,
  a non-polynomial operator, a missing conjugate) and General U(1) (a syntax
  error, a built-in name collision, an undeclared mass relation). Both are
  defects the validation report names outright.
- **What it did not fix.** Seven of the nine open models fail
  `CheckDiagonalMassTerms`, with the mass spectrum inconclusive as a result.
  These are models where the agent mixed fields it had declared as separate
  mass eigenstates: Higgs-singlet mixing (B-L, pNG dark matter, the dilaton
  model), a seesaw sector (pSPSS, W'), or a scalar leptoquark potential
  (SLQrules). Each repair agent recognised the problem and declined to
  rotate the fields blind, which is the right call under the rule that
  repairs must not change the physics. The remaining two are a 331 model
  that never compiled and an ALRSM model that times out at 900 s.
- **What this means.** With real checks, the repair loop fixes syntax and
  bookkeeping and does not fix mass-basis physics. The taxonomy from the old
  analysis holds for the first kind of defect; its pass rates do not.

## 4. How this was run

Both headless agent CLIs on the benchmark machine were logged out, so every
agent run is a Claude Code subagent of an interactive session, with the tool
policy given in the prompt and checked afterwards from the transcript
(`subagent_bench.py prepare/ingest`). Validation is serial on one Wolfram
kernel. Never run two validations at once.
